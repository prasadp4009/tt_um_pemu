## 3. RTL-needing proposals (NOT committed — decision items only)

### 3.1 T17 Option B — implement 65536/1M presets with saturation (only if the ISA lead wants the presets)

Exact fix (PE only, `src/tt_um_pemu_pe.v`):
1. Widen `wait_timeout_r` and `ecnt` from 13 bits to 21 bits (1,048,576 needs bit 20 for the value itself).
2. Timeout map: tsel 0 → 256, 1 → 4096, 2 → 65536, 3 → 1048576; remove the `instr[14]` CONFIG_ERR set for tsel 2/3 (keep CONFIG_ERR for genuinely reserved encodings elsewhere).
3. Elapsed write, both exits: `Rd <= min(elapsed, 16'hFFFF)` — i.e. on timeout write `16'hFFFF` (not the timeout value) with TIMEOUT sticky set; on a hit write `min(ecnt+1, 16'hFFFF)`. TIMEOUT sticky already disambiguates a saturated timeout from a genuine 0xFFFF hit only when combined with the sticky bit — document that TIMEOUT must be read alongside Rd for tsel 2/3.
4. Spec updates (docs-only, same change): ISA timeout table, T2, `isa_v0.2.yaml` `wait_tsel_map`, and the T17 row — a semantics change, so it forces an ISA version bump per ISA_v0.2 §10.

Re-verification cost: update `test/tb_pe.v` Part 4 (tsel 2/3 CONFIG_ERR checks become 65536/1048576-cycle timeout checks — 1M-cycle Verilator runs are cheap); update the golden model `sim.py` WAIT path and re-run all golden protocol tests; re-record any co-sim traces containing WAIT (cycle counts change only for tsel 2/3 images; none of the shipped protocol images use tsel 2/3 — UART uses tsel ≤ 1 everywhere per its header); full regression gate (643 benches, formal 32/32 incl. F4 WAIT properties, 11/11 co-sim); one CI round (gds/precheck/gl_test/test/docs, ~40–70 min). No GDS-significant change expected (small PE logic delta), but CI re-hardening is mandatory because `src/` changed. Zybo re-proof is not required unless firmware changes (it does not).

### 3.2 PULSE pin_sel wiring (item 7c)

Add a `pin_sel_r` output to the PE port list, wire it to the observer `pin_sel` input in `src/tt_um_pemu.v` (replacing the `3'b0` tie), re-run observer + top benches + one CI round. Small, but it is an RTL change and was not made in this pass.

### 3.3 UART TX starvation timeout (item 3b, firmware — not RTL)

If the 0xFFFD abort is wanted: add a WAIT-bounded starvation timeout to the TX data-wait loop in `masters:firmware/uart/uart.asm`, re-assemble, re-run golden UART + co-sim UART (8,747 cycles, trace re-record), full regression gate. Firmware-only; no `src/` change, but it does change a shipped `.hex`, so it needs the same gate discipline as an RTL change.

## 5. Bottom line — what still impacts chip functionality after this pass

**No unhandled chip-functionality bug remains.** The complete list of functionality-affecting items is:

1. **Slow-corner timing (item 4)** — the one genuine silicon-risk item: guaranteed setup across all corners needs **≤ 43.8 MHz**; 50 MHz is good at typical/fast only. Mitigation is the clock guidance, not a redesign (redesign out of scope).
2. **T17 (item 1)** — a decision item, not a bug: the as-built behavior (256/4096 + CONFIG_ERR fallback) is safe and proven; the ISA lead must choose Option A (rule the presets out, zero cost) or Option B (implement + saturate, cost in §3.1). Until ruled, firmware must not use tsel 2/3 expecting a 65536/1M timeout — it will get 256/4096 + CONFIG_ERR instead.
3. **Documented limitations (items 2, 3b, 5, 7c, 7e)** — CAN DLC ≤ 2; UART TX host-starvation blocks instead of aborting with 0xFFFD; SPI @125 MHz passed 2/2 on the 512 build but is observed-not-root-caused (proven point is 50 MHz); PULSE-mode trigger watches pin 0 only; full USB device stack / 10BASE-T out of scope. Each is bounded in `docs/CHARACTERIZED_LIMITS.md` with the exact behavior a user or judge will see.

Everything else in the table is non-functional, administrative, verification depth, or already closed. The remaining **score** item (not a chip bug) is the **Observer hardware capture (item 6)**; the remaining **admin** item is the **formal competition entry (item 7f, deadline 2027-01-18)**.
