Tarang simulator

Run the chip's firmware in your browser.

A cycle-exact port of the Tarang-32 golden model (ISA v0.2 + v0.3 9-bit activation) with the as-built RTL divergences: WAIT tsel 2/3 fall back to 256/4096 cycles + CONFIG_ERR (no 65536/1048576 presets, no saturation); illegal opcodes, CALL overflow, RET underflow and AND fn=11 are NOP + CONFIG_ERR; Observer PULSE watches PIN 0 only; trace SRAM saturates at 204 entries and never wraps. Plain HTML/CSS/JS — no external requests, no CDN. The peer models are ports of the golden test peers, so each example runs against the same device behaviour the golden model used.

Playground

READY
  1. SPI is loaded. Press Run, or pick another example below.
  2. Watch the chip. Registers, pins and the waveform update live.
  3. Dig deeper. Step cycle-by-cycle, or open the trace and die panels.

Keyboard: Space Free-run / Pause · S Step Cycle · I Step Instruction · N Run N · R Reset. Shortcuts are ignored while typing in the editor or any input, and while a button has focus.

Speed paces Free-run only; Run (until HALT) always runs full-speed. Step Cycle advances exactly one clock cycle. Step Instruction completes the in-flight instruction (a multi-cycle WAIT runs to its exit instead of looking frozen). Run-N executes exactly N cycles, then pauses with registers, PC, waveform and CAP trace at that exact point — unless the program halts first, in which case it stops at HALT. HLT itself performs no tick (clocks gated), exactly as in the golden model, so Step Cycle on HLT leaves the cycle counter unchanged.

Waveform — 8 logical pins vs cycle

20 ns per cycle. The time axis is labelled in ns/µs. The red cursor is the current cycle. On touch devices, swiping over the waveform scrolls the page; use the Window selector and the scrub bar below to move and zoom.

Scrolling, zooming, or mouse-wheeling the waveform pauses auto-follow until you re-enable it (checkbox or Follow button).

Trace RAM — Observer capture (separate from the live waveform)

  
This plot shows only what the Observer captured: one stepped
  trace per pin, plotted against the CAP timestamps of the trace entries
  themselves — not a resampling of the live waveform. The live waveform
  above and this plot share the same time conventions (20 ns/cycle,
  timestamps in the same prescaled time base), so a capture can be
  compared against the live run.

  
Trace semantics (ISA v0.2 §6, as built): 204 entries of
  {32-bit timestamp, 8-bit pins} in the 1024×8 trace SRAM; the pointer
  saturates at 204 and never wraps; on full, capture stops,
  triggers are ignored, and TRACE_FULL sticky is set. TRACE_WM is sticky
  and clears only via OBS_CLR. Try the “Observer PATTERN capture to full”
  teaching example to see the full state. PULSE mode watches PIN 0 only
  (the top level ties pin_sel to 0), regardless of PIN_SEL.

Semantics notes (what this port does and does not do)

  
    
    
  • Golden-model core, RTL divergences. Cycle timing,
    2-FF synchronizer, open-drain + pull-up resolution, FIFOs, flags,
    branches, CALL/RET stack (4 deep), Observer trigger modes, prescaler
    and CAP snapshots follow firmware/tools/sim.py and ISA v0.2/v0.3.
    Where the RTL differs from sim.py, the RTL wins (see the header
    above and tempo-core.js).
    • 
    
  • No host port model. The web simulator loads the
    program directly into IMEM and preloads the RX FIFO from the golden
    test's host stream. Host commands (LOAD_IMEM, RD_TRACE, GO/HALT_REQ)
    are not modelled; the Observer trace is shown from the PE side
    (OBS_PTR + entries), which the real PE cannot read (Q4) — the web
    view is a debugger's view, not a PE-visible register.
    • 
    
  • Observer commit timing. The golden model commits
    trace entries in the same cycle as the trigger; the RTL bound is
    trigger→commit ≤ 6 cycles with 1 trigger / 5 cycles sustained
    (bursts coalesce latest-wins). The web simulator follows the golden
    model (same-cycle commit); entry timestamps may therefore sit up to
    a few cycles earlier than the RTL would stamp them.
    • 
    
  • STATUS[12] TRACE_WM is shown in the MRS STATUS
    read (RTL/ISA behaviour); sim.py's sreg_read masks it out, a sim
    quirk that does not affect the SPI/USB validation (neither example
    arms the Observer).
